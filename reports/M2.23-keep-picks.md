# M2.23: a reparse keeps a pick while its readings are offered

- **Landed:** 2026-10-25, built in `40e7144`, with the review's fixes after it.
- **Versions:** parser version 19, page key 2, index checks 10 and cache schema 8 are unchanged: nothing a parse outputs or a key hashes changed.

## What was built

- `Picks.reconcile(results:)` judges each pick on the pages given by the rule `Output.judge` reads picks with (the pick's block still offers the same readings, joined across its unsure words). It keeps the pick that holds and deletes the others, reading and deleting in one transaction, and returns the counts by page key.
- The runner calls it right after `Store.replaceResults` of each chunk, against the results the cache holds then (so a page that kept its old result because the new reading failed keeps its picks), and prints one `picks\t<key>\t<kept>\t<cleared>` line for each key that had picks.
- `Reader.reparse` sums the lines over the chunks. `pdf reparse` says `kept N picks, the readings are the same` and `cleared N picks, the readings differ`, and `--json` has `picksKept` and `picksCleared`. The clearing at the end of the command is gone.
- Docs: F8, F10 and the `--help` of `reparse`; the DESIGNS revision note of the reparse decision (dated 2026-10-25); ROADMAP tick; the guide line reads "Keeps picks that still apply." (1,993 tokens by the reviewer's count, under 2,000).
- **Stale picks over replaced readings.** Before: a killed run left the picks of every replaced chunk until the next reparse. Now the window is the few statements between the replacement and the check in one runner. The two databases (the cache and the picks') cannot share a transaction, so it is not zero: a pick left in it does not apply (a read ignores it), and the next reparse of the page settles it.

## Review findings and resolutions

| # | Finding | Resolution |
|---|---|---|
| M1 (medium, design) | An OCR round trip loses the pick: `reparse --page 2 --step ocr` clears it, a plain `reparse` brings back the same readings, and the pick is gone. F10 itself recommends that round trip. | **Open, for the user to decide.** The rule stays as the user set it. The option not taken: never delete a pick on reparse, since every reader ignores one that does not match; the round trip loses nothing, the gap between the databases and the failed check go, and `picksKept`/`picksCleared` only count what applies now and what no longer does. Cost: stale rows pile up, and a pick whose readings return applies again. In DESIGNS.md (revision note) and plan/TODO.md. |
| L1 | Pick counts reset when the file changed between chunks; the error for a shorter new version said nothing of the replaced chunks. | Fixed: the tallies run on across the change; the summary says how many pages of the version before were replaced; the "out of range" error names the pages replaced and picks cleared (`ReadError.changedWhileReading`). Test with a file swapped after the first chunk cleared a pick. |
