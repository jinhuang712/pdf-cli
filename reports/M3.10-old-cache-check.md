# M3.10: the old-cache check

Closes the TODO item from the M2.26 review: a new table skipped on a schema-9 cache broke every command, and every test opened a fresh store. A test script, so no reviewer.

## What was built

`testdata/scripts/old-cache-check.sh <old-commit>` (run one at a time; about 3.5 minutes each, two debug builds and the scan parsed twice):

1. Adds a scratch worktree of the commit outside the repo and builds it there.
2. With one fresh `PDF_CLI_HOME`, the old binary adds four files (a paper with an unsure block and a table, the NACA scan, `carries-comments.pdf`, `hidden-color.pdf`), reads each with `--full`, runs `info` and two searches, then `pdf pick` and `pdf transcribe` (a table).
3. The new binary does the same on a second fresh home, and its reads, searches, `info`, `ls` and `crop` are the reference.
4. The new binary runs on the old home. It waits until no read says "provisional" (pages of an older parser are read again in the background; this took a few polls on 2 of 4 files), then checks: exit codes (read 0, 2 or 3, the rest 0) and equal to the fresh run's; no `Error:`, SQL or sqlite text on stderr; stdout equal to the fresh run's (home path normalised); the pick and transcript shown in place; `pick --dry-run` says it would replace the old pick; `reparse --page 1` and `reparse --step ocr` on the scan end as on the fresh cache and keep picks and transcript; `doctor` says cache ok, library ok, no problems; `clean --dry-run` leaves both databases' dumps unchanged; every table and column a fresh cache has exists in the old one; no stray runner. It prints the tables and columns the new build added.
5. Kills strays, removes the scratch worktree and the work folder, prints `ok`/`FAIL` lines, ends non-zero on a FAIL.

The new build opens all three, re-reads old pages (2 of 4 files showed "provisional" on the first read) and then gives the fresh cache's output.

## Findings

- Nothing in the new build broke on an old cache. The script found no code defect.
- Two script mistakes fixed on the way: a comment that swallowed `esac`, and the scan's page 1 read ending 3 on a fresh cache too (the exit code is now compared with the fresh run's, not fixed at 0 or 2).
- `read` on an old cache gives a provisional answer until the old pages are re-read; that is by design, and the check waits it out.

## What it cannot check

- Caches made by a commit whose `PRAGMA user_version` differs (all three are 9); a schema bump needs its own old commit.
- Whether the check would have caught the M2.26 break: b466d84 is the case, but the fix is already in the new build, so it was not run against the broken build.
- Concurrent opens of an old cache by two commands, a damaged old cache, and files outside the four used.
- The catalogue of scripts has no README; the script's header comment is its description.
