# M1.1 — Worker processes and the cache

- **Landed:** 2026-10-15 in `2cbbf20`. The review fixes are in the same commit.
- **Written:** after the fact, on 2026-10-15.

## What was built

- Commands read pages through a SQLite cache (GRDB), keyed by page content and parser version. A command never opens PDF content itself.
- A short-lived runner per file starts worker processes. It stops a worker that spends 30 s on a page or passes 2 GB of memory, retries a crashed page once in a fresh worker, and saves the results. The requested page comes first, and the rest follow in the background.
- Page keys hash each page's boxes, content streams and resources through Core Graphics, so a highlight appended to a file keeps every key.
- A result is saved only while the file keeps the size, date and inode it had when indexed.
- Hidden `pdf debug-pages` reads pages through the cache. `scripts/test.sh` runs the unit tests with the Command Line Tools, and `scripts/test-cache.sh` checks hangs, memory, crashes, moved files and concurrent commands end to end.

## Measurements

| What | Result |
|---|---|
| First page of a new 456-page file | 0.73 s |
| A page read from the cache | 20–30 ms |
| Universal binary for macOS 11, both chips | 14.5 MB |
| A hanging page, runaway memory, a crash | each costs that one page; the rest of the file reads |

Found while testing:

- **PDFKit saves damage text.** A highlight saved through PDFKit, the way Preview saves one, re-embeds the fonts in MacRoman without their Unicode maps (checked with `pdffonts`). "∗" read back as "→", and the maths letter "𝑒" as "!". The user chose to treat such a file as new and warn about it: `8c0a290`, and the DESIGNS decision on files PDFKit saved.
- **"database is locked"** when three commands open a new cache at once. Fixed in the same commit.

## Review

The reviewer reproduced finding 1 and traced the rest.

| # | Finding | Verdict | Resolution |
|---|---|---|---|
| 1 | A file that changes or disappears during a parse leaves wrong results cached for good. A worker's open failure was saved for every unreported page, a shorter file saved "could not read this page", and a file changed after indexing saved its new text under the old keys. Moving the file mid-parse cached "damaged" for pages 6–19, and a fresh copy of the file got the same. | High, confirmed | Fixed: every save first checks that the file still has its indexed stat. An end-to-end check moves a file mid-parse. |
| 2 | A limit kill can fail the next page: the worker had already reported page p and started p+1 when the kill landed. | Medium, likely | Fixed: the runner records the page it stopped (`stoppedPage`) and blames only that page. |
| 3 | Short-lived trouble becomes a permanent failure: a failed spawn cached as a file or page failure, an index crash not retried, and a slow open (an iCloud file downloading) cached as damaged after three silences. | Medium, likely | Partly fixed: a failed spawn puts its pages back and the runner stops after 3, caching nothing; an index crash gets one retry in a fresh worker. A file whose opening stays silent three times still fails as damaged; logged in TODO. |
| 4 | A runner whose lock a second runner took over keeps parsing beside it. | Low, possible | Fixed: the heartbeat checks that it still holds the lock, and the runner stops when it lost it (`lostLock`). |
| 5 | Workers outlive a runner that was killed. | Low, possible | Fixed: a worker exits when its parent changes (`getppid`). |
| 6 | An index retry can step back below a page that already failed. | Low | Fixed: `start = max(start, …)`. |
| 7 | A page key can depend on which pages the keyer hashed earlier, through memoised digests cut short by a loop or the shared budget. | Low | Fixed in `2cbbf20`; not re-checked for this report. |

The reviewer found these clean: the inbox drain, batching and requeueing, pipes and file descriptors, reaping, immediate transactions, and the command's wait loop.

## Tests

12 unit tests and 13 end-to-end checks passed, three runs in a row after the fixes.
