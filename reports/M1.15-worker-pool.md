# M1.15 — One pool of worker slots for the whole Mac

- **Landed:** 2026-10-15 in `2665352`, with review fixes in `ecf5a7f`.
- **Written:** after the fact, on 2026-10-15.
- **Why:** the user's Mac lagged while test runs parsed with one worker per performance core. The user asked for a worker pool that does not drain the laptop.

## What was built

- Every parse shares flock slots in `<cache>/slots/`: half the performance cores, at least 2. That is 2 on this M3, which has 4 performance cores.
- Slot 0 is kept for pages a command waits on.
- Workers for pages nobody waits for enter macOS's background state (`PRIO_DARWIN_BG`). They leave it on SIGUSR1, which the runner sends when a command asks for one of their pages.
- A command hands its pages to the runner it starts (`--pages=`), so the first batch knows them.

## Measurements

| What | Result |
|---|---|
| First page of a new paper / the next page | 0.78 s / 0.08 s |
| Page 2 of the OCR-repaired paper, before and after promotion | 2.1 s → 0.52 s |
| That 18-page paper parsed in the background / waited on in full / before the pool | 49 s / 8.2 s / 6.9 s |
| A CPU loop at background priority | 2.4× slower |

Background priority keeps work on the efficiency cores. That comes from [Eclectic Light's measurements](https://eclecticlight.co/2025/05/09/what-is-quality-of-service-and-how-does-it-matter/), not Apple's documentation; the CPU loop above fits it.

## Review

The reviewer reproduced finding 1. A guard in its session refused `swift test`, so it ran no tests.

| # | Finding | Verdict | Resolution |
|---|---|---|---|
| 1 | Asking for page 0 sent `--pages -1`, which the argument parser read as a flag. The command failed after about 6 s with a vague error instead of "out of range". | Confirmed, regression | Fixed: the runner gets `--pages=<list>`. |
| 2 | Background workers kept the 30 s wall-clock page limit, so a page throttled in the background could be cached as failed for good. | Likely, high | Fixed: a page that runs out of time in the background gets one more try at full speed. A log check confirms the retry path. |
| 3 | While the index waited for a slot, the sample worker beside it went unsupervised and kept its slot after exiting. | Likely, low | Fixed: the wait keeps stepping the sample worker. |
| 4 | The promotion check in `test-cache.sh` was racy: it read a line the worker writes at background priority. | Likely, low | Fixed: it reads the runner's own log line. |
| 5 | DESIGNS said the pool caps the whole Mac; it caps one cache folder, so each user has their own pool. | Doc gap | Fixed in DESIGNS. |
| 6 | With a pool of 1, slot 0 is not kept apart; the code said so, DESIGNS did not. | Doc gap | Fixed in DESIGNS. |

## Tests

58 unit tests passed, 4 of them new for the pool. The end-to-end checks passed twice in a row, with new checks for three files at once never running more than 2 workers, a waiting command promoting a background worker, and the full-speed retry.
