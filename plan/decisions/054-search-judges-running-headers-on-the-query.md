# 054. search judges running headers on the query

Decided: 2026-10-25    Status: current

`pdf search` found a running header, footer or page number on every page (M2.5, noted in plan/TODO.md). A page is indexed when it is parsed, before the pages around it say what repeats, so the index cannot hold the judgement. M2.22 judges on the query: the search lists every block that matches (no snippet yet), `Furniture.find` judges the pages of those blocks against the pages within 4 that are parsed now (the rule `pdf read` uses, chunks of 40 pages), the hits on furniture are left out and counted in the first line with `--show headers`, which brings them back labelled, and the snippets are read for the hits shown only. The index, the parser version and the index checks stay as they are. A keyword search of a 492-page report (NIST SP 800-53) on "security" took 0.9 s in the debug build against 0.2 s before, and left out 490 hits (the first build; the review's fixes follow). In the release build a search for "the" in the 625-page memoir manual (3,678 hits) takes 0.22 s before and 0.91 s after, 32 MB and 36 MB, with each chunk of 40 pages in its own autorelease pool (53 MB without it); the review measured 5,000 pages at 6.9 s and 14.1 s, 258 MB and 460 MB, before that pool. The whole hit list is judged before `--top` or the budget cuts it, so the left-out count and the total are exact; judging lazily would make both lower bounds. A pattern search judges the pages it decoded, with no second read. The review's other fixes also change what `pdf read` sets aside (judged on read, so no stored output and no parser version): a block that starts with a raised note marker is a footnote, never furniture (the six "^{2}Second note of page N" footnotes of testdata/notes/restart-per-page.pdf were footers), and the side margin counts text set sideways only (the KOMA guide's margin notes `scrbook,` and `scrlttr2` were publisher stamps). The smoke set reads the same as before. on the 10 arXiv papers of the smoke set the hits are the same as before except the arXiv stamp and a page number. Nothing repeats until the neighbours are parsed, so a header can show in a search of a file still parsing, which says so; a hit is dropped only where a read would set the same text aside, so a search and a read agree, and where the rule is wrong both are. A fallback to some of the words runs only when no block holds every word.

Options it beat:

| Option | For | Against |
|---|---|---|
| **Judge on the query, over the parsed pages** | Same rule and same answer as `pdf read`; always current as pages parse; no stored state, so no index version and no stale mark; a library-wide search is the same loop per document. | Reads the pages of every matching block (0.7 s more for 3,678 hits in 625 pages, release build); the whole hit list is judged before `--top` or the budget cuts. |
| Mark furniture in the index once a document is parsed | A query stays one SQL query. | A mark is stale as soon as a page is added, reparsed or picked, so it needs rebuilding with the neighbours' every change (a page's furniture depends on 8 others); a second copy of the judgement to keep equal to `read`'s; index checks 12 and a migration; nothing to mark while the file parses, the common case for a first search. |
| Leave the header text out of the index when the page is parsed | The smallest query. | Needs the neighbours at parse time, which the parse never has (a page's parse must not depend on another's), and `--show headers` could not bring them back. |
