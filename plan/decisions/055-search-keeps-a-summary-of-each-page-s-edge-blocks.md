# 055. search keeps a summary of each page's edge blocks

Decided: 2026-10-26    Status: current

M2.22 judged running headers on every query and read every page that has a hit, plus the pages within 4 of it: 0.60 s for "the" in the 625-page memoir manual (607 pages cached) (release build; 0.22 s before M2.22), and the review's 5,000-page and 6,402-page libraries took twice as long as before. `Furniture.find` reads only each page's few edge candidates (at most 4 an edge), its label and, for the page itself, whether a sideways margin block is arXiv's stamp. M2.26 stores exactly that, `Furniture.Summary` as JSON, in table `search_edge (page_key, parser_version, data)` beside the index, one row for each page result ("-" for a page with no layer, about 150 bytes a page: 90,561 bytes for the memoir manual's 625 pages against 4.7 MB of results). `insertResult` writes it in the transaction that indexes the page; a trigger on `page_result` deletes it with the result, as the index's trigger does, so a reparse (`replaceResults` deletes the old result, then inserts the new) replaces it, and `rm`, `gc` and a parser-version change remove it. A page cached before the table existed has no row: the search makes the missing summaries of the pages it needs from their results and stores them (a failed write fails nothing), so the first search of an old cache costs about half the old query (0.28 s against 0.60 s) and the next the new one. The judgement itself is the same function: `Furniture.find` on a layer builds the layers' summaries and calls the summary form, so `pdf read`, which reads its layers anyway, and `pdf search` cannot disagree. Hits, counts and `--show headers` are byte-identical to M2.22's on the memoir manual for "the", "chapter" and "figure". A pattern search still judges the layers it decoded. The summary carries a version (`Furniture.summaryVersion`, 1, in the JSON as `v`): a row of another version or one that does not decode counts as missing and is replaced when the search makes it again (the review: a rule change, or a new field, left old rows in force and search disagreed with read). The table and its trigger are created with `IF NOT EXISTS` on every open of the cache, outside the schema version's guard, because the schema stayed 9 and a cache made before the table has the version and not the table (the review's high finding); raising the schema to 10 would have worked too, but would have made every cache run the whole migration, and two builds sharing a cache would then fight over the version. The index checks stay 11: none of the checks a file entry runs changed, and re-indexing a file does not fill the table, so a bump would only re-index every file (M2.22's note that they would go to 12 is withdrawn). `Store.indexForSearch` reads whether the page is new right after its `search_page` insert, as the summary's own insert changes a row too.

Options it beat:

| Option | For | Against |
|---|---|---|
| **Store each page's edge summary; judge from summaries on the query** | The judgement stays on the query, so it is always current as pages parse and equal to `read`'s; a hit costs a row, not a decoded layer; a page's summary depends on its own layer only, so it goes stale only with that page's result, which the trigger handles. | A second table; old caches fill it on first search. |
| Store the verdict (which blocks are furniture) | One lookup a hit. | A verdict depends on 8 pages and changes as neighbours parse, reparse or are added: the stale mark M2.22 rejected. |
| Leave as is (judge from layers) | Nothing stored. | 2 to 4 times the time of the plain search, growing with every page that has a hit. |
