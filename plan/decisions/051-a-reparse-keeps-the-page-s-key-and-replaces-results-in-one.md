# 051. a reparse keeps the page's key and replaces results in one transaction per chunk

Decided: 2026-10-25    Status: current

Revised 2026-10-25 (M2.21): the decision first said one transaction for the whole command; the unit is now a chunk of 50 pages, the rest unchanged.

`pdf reparse` (M2.10) reads pages again in a runner of its own, through the shared pool, and the cache replaces their results in one transaction once every new reading of a chunk is in. A chunk is the unit: the pages go in chunks of 50 (M2.21), each read in a runner of its own and replaced in one transaction, so a run that is killed keeps the chunks it finished and changes nothing in the chunk it was on, and a run stops starting chunks after 90 s, says how many pages it left and prints the command for them (exit 2). The page keeps its key, which holds what the page draws, so a transcript, kept by that key, shows again beside the new reading, and the file's index and its document ID do not change. `--step ocr` runs the worker's OCR path for every page asked for and stores the result under the same key. A pick is the agent's choice between two readings the old parse offered. *Revised 2026-10-25 (M2.23, replaced by the revision after it):* the runner, right after it replaces a chunk, checks each pick on the chunk's pages against the page's result now in the cache, by the rule a read applies a pick by (the block still offers the same readings), keeps the ones that hold and deletes the others, and prints how many of each; the command adds the chunks up and says so in the summary and `--json` (`picksKept`, `picksCleared`). It beat clearing every pick on the pages read (the first rule, which lost the agent's work when the new reading was the same) and a check once at the end of the command (a killed run left the window below). The picks are in the agent's database, the results in the cache, so the two cannot share a transaction: a runner killed between its replacement and the check, a gap of a few statements, leaves picks that no longer apply, which a read ignores, and the next reparse of those pages settles, since the check is repeatable. Before M2.23 the window was the whole run. A check that fails (the picks' database is locked) is named in the summary, with the pages and the command that checks them, and the command ends 1. The delete is made only if the row is still the one that was judged, so a `pdf pick` made at the same time against the new reading stays. *Revised 2026-10-25 (M2.24, the user chose this option):* a reparse never deletes a pick. Every reader already ignores a pick that does not match (`Output.judge`), so an OCR round trip (`reparse --step ocr`, then a plain `reparse`, which F10 itself recommends) loses nothing: the pick applies again when its readings come back. The runner still looks at the picks of the chunk it replaced, read-only (`Picks.tally`), and the command prints counts of what applies now and what no longer does (`picksApply`, `picksStale`; `picksCleared` would have lied, as nothing is cleared, so both old names went). The gap between the two databases, the delete, and the failed check (and the exit 1 it caused) are gone: a picks' database that cannot be read leaves the counts out (`picksUnknown`, and the counts are null in `--json`) and the reparse is done; the library list, which is the same file, is written after the run and a failure there (`libraryFailed`) no longer ends the command without its summary. The picks' table key became (page key, block, reading a, reading b), so a `pdf pick` for other readings of a paragraph does not replace a stored pick that does not apply; an older table is migrated with every row kept (M2.24 review). The cost: stale rows stay in the picks' database, and no command removes the picks of a page that never comes back (FEATURES.md F10 Gap). The runner holds its own lock, `reparse:<path>`, not the file's, so a runner that parses the rest of the file may go on: a result is never missing while it is replaced, and an `INSERT OR IGNORE` of an old reading finds the row there. The runner ends when its command goes (its parent changes), and the command starts it in its own process group, so Ctrl-C stops both: nothing is left parsing, and no chunk is half replaced. A new reading that failed never replaces one that read well, and the command ends 2 and counts it. It never takes the pool's slot 0, so the first page of a file another command waits on is not starved (0.87 s against 0.76 s alone, with a 30-page OCR reparse running). It stores no failure for a locked file: the file's cached results stay, and the failure line names `pdf reparse <pdf> --password-stdin`. A file too big for the agent's command limit (about 300 OCR pages, 400 pages with lost spaces) no longer has to be split by hand: the time limit ends the run between chunks and names the pages left. Pages with one key share a result, so a later chunk may read again a result an earlier chunk replaced; the report's `before` is read once, before the first chunk. The chunk size and the limit have test hooks, `PDF_CLI_REPARSE_CHUNK` and `PDF_CLI_REPARSE_TIME_LIMIT`.

OCR reads PDFKit's rendering, which draws text under an annotation and in a layer switched off. A page read by OCR, with or without a reparse, puts the OCR lines that lie over words the text layer hides under a hidden run, so they stay under their marker, out of search, and counted (parser version 19).

It follows "Same file, same answer" and "Failure is loud": a page the new method cannot read keeps what it had, and the output names it.

| Option | For | Against |
|---|---|---|
| **Same key, replace in one transaction per chunk of 50 pages** | Transcripts stay at once; atomic; the library, the index and the document ID are untouched. | A copy of the file, or another file with an identical page, shares the new result; its picks on that page are counted by the reparse that replaces it, and a pick made through a copy applies by the same rule. `--step ocr` stores OCR under the key of a page with a text layer. |
| Delete picks that do not match after a replacement (M2.23, the rule before M2.24), or clear every pick on the pages read (the first rule) | The picks' table holds only picks that apply; the counts say what was lost. | An OCR round trip loses the agent's work though the readings come back; the two databases cannot share a transaction, so a gap and a failed check needed their own error path. |
| A new key for an OCR reading (`PageKeys.ocr`), and a new document | Another copy is not touched; the method is in the key. | The document ID changes, so the library entry, `pdf ls` IDs and every page's transcripts move with it; transcripts are keyed by the old key and vanish. |
| Delete the old results, then parse | One path, as a normal parse. | A crash or a Ctrl-C leaves pages with no result, or a failure in place of one that read well. |
| Parse in the command's process | No runner. | PDFKit opens the file in the command, which the tool never does: a hostile PDF could stop it (DESIGNS.md → Principles → Safety). |
